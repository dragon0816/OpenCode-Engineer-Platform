# Phase 3 需求：多助理、能力、記憶與 Share Platform

2026-11-22。擁有者看過 GUI 重做（分步 1 至 3，版本 0.1.0）後提出。本文件記錄需求原意、技術分析、衝突分析與待決事項。決議後追加到 `docs/DECISIONS.md`，任務拆解寫入 `docs/TASKS.md`。

## 1. 需求原文整理

### 1.1 LLM Gateway
- R1：接入外部的 Claude Code、Codex、Copilot，補 Gateway 模型的不足。
- R2：Gateway 上有的模型（例如 qwen 27B、GPT-5.5、GPT-5.6）要列出來讓使用者選。

### 1.2 助理（Agent）管理
- R3：建立新助理的方式。
- R4：說明主要工作區與獨立工作區的差別。
- R5：支援多助理，每個助理可選擇綁定對外的 Telegram bot 或 WhatsApp bot。
- R6：可設定助理引用哪些知識庫。
- R7：觸發方式支援訊息觸發、定時觸發，或兩者並存。需要分析衝突。

### 1.3 能力（Capabilities）
- R8：Skill、Workflow、MCP 的發佈與安裝，要和 Share Platform 連結。這裡的 MCP 是客製 MCP：通常編成執行檔發給使用者，在本機執行，並提供 FastAPI 給助理使用。
- R9：Plugin 下載與安裝。Plugin 比上述三者複雜，由多個 Skill、Workflow、Python 程式和操作畫面組成，例如知識庫建立流程。Plugin 只由 OEP 開發團隊提供，不開放使用者開發。
- R10：知識庫可從 Share Platform 取得並安裝。安裝後在設定助理時指定要引用的知識庫。知識庫的建立與發佈由 Knowledge Wiki 或 BI Knowledge plugin 實現。
- R11：自我成長：從使用者的工作內容找出常用做法，產生 Skill 建議，由使用者自行套用。
- R12：依 Share Platform 的設定，連線取得 Skill、Workflow、MCP。

### 1.4 記憶
- R13：可標記並保存使用者認為重要的會話。
- R14：可累積的資訊，例如名片。通常由 Skill 或 Workflow 指定把助理產出存到特定的 SQLite 資料庫或 JSON 檔。

### 1.5 設定
- R15：定義自動產生 Skill 的規則。
- R16：多助理的綁定設定。
- R17：Share Platform 的位置。

### 1.6 審核與 BI Knowledge
- R18：說明審核與 BI Knowledge 的連結機制：Telegram bot 如何驅動 BI 卡片處理流程、如何進入審核、審核後如何加入 BI Knowledge。

### 2.1 主要工作區與獨立工作區（R4）
兩者都是 OEP 管理的本機工作資料夾，助理在對話中讀寫的檔案都放在這裡。差別只在「彼此隔離」：
- 主要工作區：舊會話預設都在這裡，日常工作用。
- 獨立工作區：另一個乾淨的資料夾。在這裡的會話看不到主要工作區的檔案，適合試驗、或不想和日常檔案混在一起的工作。

這個設計是單一助理時代的暫時做法，名稱也不直觀。改成多助理後，建議「每個助理有自己的工作資料夾」，取代固定的兩個工作區（見 4.1）。

### 2.2 審核與 BI Knowledge 的現有流程（R18）
1. 使用者把連結或檔案傳給 BI Telegram bot。
2. OEP 收件，存入收件匣（`bi_sources`）。需要補件時回覆使用者。
3. 背景工作依 BI 資料格式（schema）擷取內容，產生卡片候選，作為一份「提案」送到 BI 知識庫。收件狀態變成「已送審」，bot 回覆「收件 N 已送審」。
4. 工作台「審核」頁出現這份提案。擁有者逐項檢查，分兩步：先「核准」，再「發布」。
5. 發布後，知識庫產生新版本。卡片從此可以被問答與搜尋使用。bot 通知「BI 審核已發布」。
6. 沒有核准或發布前，候選卡片不會進入問答與搜尋。

注意：這裡的「BI 卡片」是市場情報卡。擁有者 AEP 截圖中的「名片」是聯絡人資料，屬於 R14 的可累積資訊，不是 BI 卡片，預設不進審核（見 4.6）。

## 3. 觸發衝突分析（R7）

訊息觸發和定時觸發可以並存。以下是會發生的衝突，以及建議的規則。

| # | 衝突情境 | 後果 | 建議規則 |
| --- | --- | --- | --- |
| C1 | 一個 Telegram bot 同時綁給兩個助理 | Telegram 同一個 bot 只能有一個接收者，第二個會一直收到衝突錯誤，訊息會被搶走或遺失。 | 一個 bot 只能綁一個助理。一個助理可以綁多個 bot（例如 Telegram 加 WhatsApp）。設定時直接擋下。 |
| C2 | 定時工作執行中，使用者剛好傳訊息給同一個助理 | 兩件事同時寫同一個工作資料夾或同一份資料，檔案可能互相覆蓋。 | 每個助理一個工作佇列，一次只執行一件會寫入的工作，其餘排隊。使用者訊息排在定時工作前面。純問答（不寫檔）可以並行。 |
| C3 | 定時工作和訊息對話混在同一個會話 | 對話記錄混亂，模型看到不相關的上下文。 | 定時工作每次開獨立的執行記錄，不插進使用者的對話會話。結果用通知送出。 |
| C4 | 上一次定時工作還沒跑完，下一次時間到了 | 同一件工作重疊執行。 | 同一個排程不重疊。時間到時如果上一次還在跑，這一次標記「略過」並記錄。 |
| C5 | 電腦關機或 OEP 沒開，錯過排程時間 | 漏跑。 | 每個排程可選「開機後補跑一次」或「略過」。預設補跑一次，不補跑多次。 |
| C6 | 定時工作需要人確認（例如要寫入知識庫） | 半夜沒人回應，工作卡住。 | 定時工作不等待人。需要確認的結果一律送到「審核」或標記「需要處理」，工作本身結束。 |
| C7 | 定時工作的結果要送給誰 | 不知道發到哪個聊天室。 | 排程必須指定結果送到哪裡：工作台通知、某個 bot 的某個聊天室，或只存檔。 |
| C8 | 兩個助理同時寫同一個累積資料庫（例如名片庫） | 寫入衝突。 | 累積資料庫一律透過 OEP 寫入，交易式、單一寫入者，並記錄是哪個助理、哪次執行寫的。 |
| C9 | 訊息重送或重複觸發 | 重複執行、重複寫入。 | 沿用現有的訊息識別碼去重。累積資料可設定唯一鍵（例如名片以 email 或電話去重）。 |
| C10 | 排程太頻繁或跑太久 | 費用與資源失控。 | 每個助理和每個排程都有回合上限與每日執行上限，沿用現有回合限制。 |

結論：兩種觸發可並存，不會有無法解決的衝突。前提是 C1、C2、C3、C6、C7 這五條規則做成系統強制，不靠使用者自律。

## 4. 建議設計

### 4.1 助理資料模型
每個助理包含：
- 名稱、頭像、簡介、個性與指示。
- 預設模型。
- 工作資料夾：每個助理一個，取代固定的兩個工作區。舊的主要工作區與獨立工作區會轉成兩個工作資料夾，舊會話不遺失。
- 引用的知識庫：可多選。只能查已安裝、已發布的版本。
- 啟用的能力：可使用哪些 Skill、Workflow、MCP、Plugin。
- 對外通道：綁定的 Telegram bot 或 WhatsApp bot。一個 bot 只能綁一個助理。
- 觸發：訊息觸發開關，加上零到多個排程。
- 可寫入的累積資料集（見 4.6）。

建立方式：左欄「助理」區塊的「＋」打開精靈。步驟依序是：基本資料 → 模型 → 知識庫 → 能力 → 通道 → 觸發 → 確認。也可從現有助理「複製」一份再修改。

現有的 Main bot 對話助理與 BI 收件流程，轉成兩個預設助理，行為不變。

### 4.2 模型清單（R2）
- 啟動時向 Gateway 查詢可用模型（OpenAI 相容的模型清單端點），結果存在本機。查詢失敗時沿用上次清單。
- 設定頁讓使用者勾選要顯示哪些模型，並設定預設模型。模型選單只顯示勾選的模型。
- 依然不顯示 Gateway 網址與金鑰。

### 4.3 外部代理：Claude Code、Codex、Copilot（R1）
這三個是「程式代理」，不是一般的模型 API。各自需要使用者自己的帳號或訂閱，透過各自的命令列工具以非互動模式執行。建議：
- 把它們當成助理可呼叫的「外部代理工具」，用來處理指定任務，例如寫程式、改檔。不是拿來取代對話模型。
- 每次呼叫只開放該助理的工作資料夾，結果以檔案與摘要回傳，並記錄在工作記錄中。
- 預設關閉。每個代理在設定頁個別啟用，並顯示「資料會送到該服務」的提醒。
- 風險：公司資料會送到外部服務；各服務的使用條款不同，Copilot 的自動化使用限制尤其需要確認。需要擁有者確認資料政策（見 6，D2）。

### 4.4 能力：Skill、Workflow、MCP 與 Share Platform（R8、R12）
- 「能力」頁分成：已安裝、Share Platform 目錄、更新、建議（自我成長）。
- 安裝來源：Share Platform，或本機檔案。安裝前顯示名稱、版本、發佈者、需要的權限，並驗證檔案雜湊或簽章。
- 客製 MCP 執行檔：OEP 下載後放在受管資料夾，驗證雜湊，由 OEP 啟動與停止，只監聽本機位址，並把位址與連線密鑰提供給有啟用它的助理。
- 發佈：使用者可把自己的 Skill、Workflow 提交到 Share Platform。提交後由平台審核。
- 權限由另一個系統管理。OEP 只負責完整性檢查、啟用範圍，以及顯示權限。

### 4.5 Plugin（R9、R10）
- Plugin 是一個簽章過的套件，裡面有 manifest、Skill、Workflow、Python 程式、資料結構與畫面頁。
- 只接受 OEP 開發團隊簽章的套件。不提供使用者開發工具。
- Plugin 安裝後在左欄「主功能」加入自己的頁面，並可註冊審核類型與累積資料集。
- Knowledge Wiki 與 BI Knowledge 改成 plugin。這是較大的重構，放在後期，期間現有功能不中斷。
- 知識庫（已發布的內容）可從 Share Platform 安裝，安裝後可在助理設定中被引用。

### 4.6 記憶（R13、R14）
- 重要會話：會話選單加「加入記憶」並可加註。「記憶」頁列出這些會話，點選後在右側開啟。助理可被設定為參考這些記憶。
- 累積資料集：由 Skill 或 Workflow 宣告一個資料集，例如「名片」，包含欄位定義、唯一鍵，以及存成 SQLite 或 JSON。助理產出時由 OEP 驗證欄位後寫入，並記錄來源會話。
- 「記憶」頁可瀏覽、搜尋、編輯、匯出 Excel 每個資料集。點選一筆資料時，右側顯示原始圖片或來源會話。
- 名片情境：Telegram 傳名片照片 → 助理辨識 → 寫入「名片」資料集 → 回覆辨識結果。預設不需審核。如果擁有者希望先確認再存，可在資料集設定「寫入前需審核」，屆時改送到審核頁。

### 4.7 自我成長（R11、R15）
- 背景分析已完成的會話，找出重複出現的工作步驟，產生 Skill 草稿，放到「能力 > 建議」。
- 使用者看過內容後才套用，可以先編輯。永遠不自動啟用。
- 設定頁規則：開關、分析範圍（哪些助理、多久以內的會話）、重複幾次才建議、排除的內容（例如含名片或客戶資料的會話）、分析使用的模型。

### 4.8 設定頁新增（R15、R16、R17）
- 能力與 Share Platform：平台位置、連線狀態、同步頻率。
- 助理與通道：bot 和助理的對應表，衝突時直接標示。
- 自我成長規則。
- 外部代理：啟用與資料提醒。
- 模型：可顯示的模型與預設模型。

### 4.9 主助理協調（Orchestrator）模式（擁有者 2026-11-22 指定）

擁有者指示：主助理擔任協調者，負責和使用者溝通，並把工作交給專職助理。專職助理只做自己的工作。使用者也可以直接和專職助理對話，代價是主助理不會有那段對話的紀錄。

**角色**
- 主助理：唯一一個，不可刪除。預設綁定 Main Telegram bot 與工作台的預設對話。它能看到所有專職助理的名稱、專長說明與目前狀態，並能把工作「交辦」給它們。
- 專職助理：各自有工作資料夾、知識庫、能力與通道。只透過交辦或使用者直接對話接受工作。

**交辦機制**
- 主助理有一個 OEP 提供的工具「交辦給專職助理」，參數是對象、任務說明與附帶檔案。
- 每次交辦都在專職助理那邊開一個獨立的執行紀錄，用專職助理自己的模型、知識庫、能力與工作資料夾執行。主助理拿不到專職助理的知識庫或工具，只拿得到交辦結果。這樣範圍邊界才成立。
- 結果回傳內容包含摘要、產出的檔案與狀態，寫進主助理的對話。右側可以開啟那次交辦的完整執行紀錄。
- 可以同時交辦給不同的專職助理。同一個專職助理依第 3 節 C2 規則排隊。
- 長時間的交辦是非同步的：主助理先回覆「已交辦」，完成後由主助理通知使用者。
- 只有一層：專職助理不能再交辦給其他專職助理，也不能反過來交辦給主助理，避免循環與失控的費用。
- 每次交辦都受回合上限限制。主助理的一則使用者訊息觸發的所有交辦，加總也有上限。

**直接對話**
- 使用者可以從左欄「助理」或專職助理綁定的 bot 直接對話。這些對話只存在專職助理那邊，主助理看不到。
- 例外：專職助理寫入的累積資料集（例如名片庫）與發布到知識庫的內容是共享資料。主助理可以透過交辦，請擁有該資料的專職助理查詢。

**觸發與協調**
- 專職助理的觸發來源有三種：主助理交辦、使用者直接對話、排程。三者共用同一個排隊順序。優先順序是使用者直接對話先，再來是主助理交辦，最後是排程。
- 專職助理的排程結果預設回報給主助理（主助理有紀錄，並由它通知使用者）。也可以設定為直接送到該專職助理的通道。

**實作取向**
- 交辦由 OEP 控制，不使用 OpenCode 內建的子代理工具。原因是內建子代理共用同一個工作資料夾和工具設定，無法做到每個助理隔離，也無法完整稽核。
- 現有的 BI 收件流程轉為第一個專職助理「BI 收件」。

**待決**
- D7：專職助理的排程結果，預設回報給主助理，還是直接送出？
- D8：專職助理之間是否完全禁止互相交辦？（建議禁止）

## 8. 預設專職助理「BI 資料處理」（擁有者 2026-11-22 指定）

3B 完成時必須內建這個專職助理，作為多助理與交辦機制的第一個實際案例與驗收情境。

- 名稱：BI 資料處理。專長說明：接收使用者傳來的資料，執行 BI 資料處理，產生 BI 卡片並送審。
- 通道：綁定 BI Telegram bot（沿用現有 BI bot 設定，不需要重新設定 token）。
- 知識庫：可寫入目標為 BI 知識庫，只能以「送審提案」方式寫入，不能直接發布。
- 流程（沿用 2.2 的現有流程，行為不變）：使用者在 Telegram 傳連結或檔案 → 收件，資料不足時請使用者補件 → 依 BI 資料格式擷取並產生卡片候選 → 送到審核頁，回覆「已送審」→ 擁有者核准並發布 → 通知「已發布」。
- 主助理也可交辦給它，例如使用者在工作台把檔案交給主助理並說「做成 BI 卡片」。交辦結果是「已送審」與審核連結，主助理有紀錄。
- 使用者也可在左欄「助理」直接和它對話，查詢收件狀態或補件。這些對話主助理看不到（依 4.9）。
- 排程（3C 後）：可設定定時處理收件匣，結果依 D7 預設回報主助理。
- 現有的 BI 收件資料、待審項目與已發布版本，轉換後全部保留，歸到這個助理名下。

驗收：Telegram 傳一份合成測試資料 → 審核頁出現候選卡片且標示來源為「BI 資料處理」→ 核准並發布 → Telegram 收到發布通知 → 主助理交辦同類資料也得到相同結果。全程只用合成資料。
